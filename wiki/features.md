# Key Features

[← Back to README](../README.md)

- **Multi-Platform Support**: Fully supports **SpigotMC**, **PaperMC**, and **Folia**.
- **Interactive GUI System**: Multi-tier virtual menus for managing identities, runes, and abilities.
- **Native MythicMobs Integration**: Abilities map directly onto MythicMobs — each ability stores an `abilityCode` (the MythicMobs ability/skill ID) and an `abilitySkin` (the model ID, with a default skin fallback). Ability items created with `/identity ability create` carry both in their persistent data, and equipping them records exactly which MythicMobs ability runs and which skin renders.
- **Dynamic Data Binding**: Ability and Rune GUIs fetch real-time data from the database, showing equipped items or placeholders.
- **Regionalized Threading**: Fully compatible with Folia's `RegionScheduler` and `GlobalRegionScheduler`.
- **Multi-Database Storage**: Identity data can live in SQLite (the zero-configuration default), MySQL, PostgreSQL, or MongoDB, selected with `database.type` in `config.yml`. All backends run fully asynchronously behind the same `IMCIdentityDB` contract.
- **Central Server Storage**: Alternatively, all identity data can live on the MCIdentity central server, accessed through an authenticated REST API over a pooled HTTP client, so every game server on the network shares one consistent data set.
- **Extensible API**: Provides a central `MCIdentityProvider` for third-party plugins to interact with the identity system.
- **Secure Commands**: Role-based permissions for administrative actions.
- **Visual Identity Keys**: Identities are represented as physical items in the game with custom colored display names.
- **Unbound Identities**: Identity items created via `/identity get` are initially "unbound". They lack a unique ID and database entry. Both the unique ID and the identity's initial stats are generated and registered in the database only when the item is first used.
- **Base "Player" Profession**: Every player permanently owns a built-in `player` profession, created automatically in the database on first join and keyed by the player's own UUID. It is the fallback state whenever an identity is unequipped, dropped on death (only when `drop_on_death` is enabled in `config.yml` — it is `false` by default), or fails to equip, so a player is never without a profession. It can never be deleted or turned into an identity key item. **Note:** The base profession is strictly hardcoded in memory. It does **not** generate a `professions/player.yml` file and cannot be modified via YAML configuration, so server administrators should not expect a config file for it.
- **Alternative Base Identities**: On top of the **Primary** base identity (which keeps the player's own UUID), players can unlock additional, fully independent `player` identities. Alternative identities are indexed 1...n and keyed by deterministic UUIDs derived from the player UUID and the index, so they fit the same database schema and can always be recomputed. Admins grant slots with `/identity base <player> <amount>` (see [Commands](commands.md)); each grant is stored per player and registers the new identities in the database immediately. All owned base identities are browsable in the paginated **Player Identity GUI** (see [GUI System](gui.md)).
- **Cold-Boot Login Protection**: When `database.type` is `central`, the central server may be hosted on infrastructure that suspends idle instances. During the asynchronous pre-login phase the plugin pings the central server's `/health` endpoint — the ping doubles as the wake-up signal for a cold server. Players are refused with *"The database is starting up. Please come back in 1 minute."* while the plugin's storage initialization (schema check and profession registration) has not completed yet, and whenever the server is offline or the request times out — so nobody joins with unreachable data or a half-initialized plugin. The initialization itself retries automatically every 10 seconds until it succeeds, so a cold-started central server only delays startup instead of breaking it. All checks run on the async login thread; the main game thread is never blocked.
- **Passive Base Leveling**: Base identities level without limit from passive playtime EXP on two tracks. The **Primary** identity gains 1 EXP per second for every online player — even while another identity (or an alternative base identity) is equipped — and levels at 86,400 EXP per level (one level per day of play time). An **Alternative** identity gains its 1 EXP per second only while it is the currently equipped identity, and levels at 3,600 EXP per level (one level per hour of active play). A second is never counted twice for the same identity: wearing the Primary identity yields only its always-on gain. Gains are buffered in memory per identity and flushed to the database in bulk every five minutes and on quit.
- **Base Profession Restrictions**: The base profession may equip skins and auras but is blocked from using runes and abilities.
- **Always-On Storage Isolation**: Each identity's inventory and enderchest are always isolated and stored with the identity; the previous `features.inventory` / `features.enderchest` config toggles have been removed.
